# Known gaps

What the client does not implement yet, or implements with an approximation it cannot confirm. Entries are removed once settled.

## Fellowships

- Stock EQEmu does not send RoF2 fellowship packets, so nothing here has met a server. Native requests and roster/vitality fields were checked against the original handlers, and against EQEmu PR #5134 "TOB: Fellowships" (open, unmerged) as a protocol reference. Unit, mock-server and both UI-pack rendering tests cover native twelve-member and expanded 64-member rosters. Live cross-zone synchronization, XP awards and camp gameplay remain untested.
- The 64-member array layout and the 1080-byte invitation are extensions beyond RoF2, documented in `docs/protocol/rof2-packets.md`. PR #5134 hard-caps its model and serializers at twelve, so its membership rule alone cannot enable 64. A server that sends expanded rosters and a live roster capture would establish interoperability above twelve.
- Declining sends action 4, as RoF2 does (`Send_Opcode_0x7121` @0x668710). PR #5134 reads action 4 as a legacy camp destruction, so against that server a decline reaches its camp handler instead of refusing the invitation; that is the server's to fix, since RoF2 sends the same. An unanswered invitation that times out sends nothing: whether the original's dialog sends action 4 on its 100-second timeout is not traced; the confirmation dialog's timeout path (dialog type 0xc) would settle it.

## Shared archive memory

- `assets.shared_memory=auto` (docs/layout.md "Shared archive memory") is measured on Linux only, one and two clients
  in one zone (docs/research/shared-asset-memory.md). Windows and macOS mapping, locking and eviction are covered by
  unit tests, not live sessions; sustained play with zoning, and more clients, are not measured. A cache file is
  checked once per client and then trusted: a file damaged on disk while a client runs is not noticed by that client
  (the parsers still bound what they read).

## Shared GPU textures

The experimental texture broker (docs/graphics.md "Shared GPU textures", docs/research/shared-gpu-memory.md):

- When sharing stops, a client copies its imports into its own images (`GpuSharedCache::localize`). That copy reads
  each import once more after the client has left the lease, and a client whose shared frame did not finish within
  2 seconds gives up the lease (by disconnecting) while that frame may still be running. Vulkan gives an external
  image to one instance at a time; both cases only read immutable images that every client keeps in
  `SHADER_READ_ONLY_OPTIMAL`, and the copy's layout change to `TRANSFER_SRC_OPTIMAL` is on the client's own image
  object, but whether a driver may rewrite such an image's memory (compression metadata) on that transition is not
  established. Khronos guidance or the driver vendors' word on external images would settle it; a validation-layer
  run of the failure paths on AMD, NVIDIA and Intel would at least rule out API misuse.
- The failure paths (broker killed, a client killed holding the lease, lease timeout, hung frame, localisation) are
  covered by unit tests of the bookkeeping and the client's decisions only, not on Windows with real GPUs.

## Network and session

- Return Home on the character select is enabled for a character whose list entry has both `go_home` and `enabled` set. The original checks `bCanGoHome` and `bUseable` (`CCharacterListWnd::EnableButtons` @0x42f4b0); that `bUseable` comes from the list's `enabled` byte is assumed, not traced. Stock EQEmu always sends `enabled = 1`, so it changes nothing there. Tracing where OP_SendCharInfo's handler fills `CharSelectInfo` +0x15c would settle it.
- The client does not send the zone-in packets that EQEmu's RoF2 table does not define (tribute, social post and similar); EQEmu servers do not need them.
- Packets with no name in EQEmu's RoF2 table (for example the opcodes behind `/shieldgroup`, `/decaycorpse`, `/uptime`, `/servertransfer`, `/acompare`, `/spellscribe`, `/offlinemode` and the veteran reward claim, the bazaar's and barter hall's Find (0x0e44), and the duel refusal) are sent but get no answer. A plain duel refusal (declined or ignored) also goes as EQEmu's 12-byte OP_DuelDecline, which tells the challenger; the refusals "already dueling" and "considering another duel" (kinds 1 and 2) are not reported on EQEmu, which itself refuses such challenges before they reach the player.
- Server files: the server script cannot see what a client has acknowledged (EQEmu's Lua has no view of the connection's resend queue), so it bounds what a client that asks for pieces and never acknowledges them makes the zone hold only by its rates: `files_chunks_per_second_zone` x 32 KB for EQEmu's 30 s resend timeout, about 1 GB at the defaults. A Lua call for a client's unacknowledged bytes, or a live measurement of the zone's memory under such a client, would settle what default is safe.
- Server files on a Windows server: the script notices a file changed in place since its hashing by its size only (a PowerShell start per file to read its time would be too slow), so a file rewritten with the same size goes with its old hash until the next listing (`files_rescan`, `#reloadquest`), and the client finds it damaged and keeps its old files. A cheap way to read a file's time from EQEmu's Lua on Windows would settle it.
- Declining a group invite sends `OP_CancelInvite`, which stock EQEmu does not handle, so the inviter is told only on a server with the Hailstone server script (`server/`). The script's relay was not tried live (the test server runs an older copy of the script). The stock handler's other step, removing the decliner from its group, is not done.
- Login: EQEmu's login server never answers 302/114 (its "already online" is 111, a plain refusal, and only with `World:EnforceCharacterLimitAtLogin`), and has no kick request (0x16) or reply (0x32): the Yes / No question, the kick and the second play request follow eqmain and are tested against the mock only. The login reply's two leading bytes (EQEmu sends 0, 0) are not copied by `LoginClient::OnPlayerLogin` and their use is unknown; the handshake reply's extra string is read and unused, as in eqmain. The server pushes 0x25 to 0x31 are logged and ignored; of them EQEmu sends only 0x31 (its OP_LoginExpansionPacketData, with `display_expansions`), which eqmain passes to LoginClient's callback +0x70 (the expansion offers, not followed).
- Server select: Play is offered for every world, whatever its status, because eqmain's play handler (`ServerSelectWnd::WndNotification` @0x10038310) and its row builder (@0x10036750) check none. Nothing else that would grey out the Play button for a down or locked world was traced, though not every caller of the button was read; seeing the RoF2 client's server select with a locked world listed would settle it.
- OP_Weblink: the original opens the address in an in-game HTML window (`WebManager_CreateHtmlWnd`, Gecko); Hailstone opens it in its own browser window (the system's browser without the helper), and only http(s) addresses (docs/browser.md). What the original does with other schemes, and the window's size and controls, are not in the export: tracing `WebManager_CreateHtmlWnd` and `CHtmlWnd` would settle them. Whether it reuses one window for a second link, and whether it limits a flood of them, is not traced either: Hailstone limits server links (`app/server_links.h`, docs/browser.md); tracing `CHtmlWnd` creation in the OP_Weblink case (@0x4c5b5d) would say whether a single window is reused. The links' tabs are the player's (as an HTML window is), but Hailstone does not open a link to this computer or the player's network and keeps their cookies apart from the player's tabs; whether the original refuses any host, or shares the HTML window's cookies with the player's own pages, is not traced either.
- The guild window's Go to URL (`CGuildMgmtWnd`, `GotoURL`): what the original does with the guild's URL is not traced. Hailstone opens it as `/url` would, only when it is http(s) (one without a scheme gets `http://`), and says so in chat otherwise (docs/browser.md). Tracing `CGuildMgmtWnd::WndNotification`'s GotoURL case would settle it.
- Login receive-idle timeout remains a client choice of 14.8 s; the original login manager sets no receive-idle limit, and what the original login owner does with a silent link is not traced. UCS follows UniversalChatProxy_Connect @0x7f0040's Params, rechecked in the disassembly (chat_server.cpp `ucs_session_options`), and the owner check in UniversalChatProxy_GiveTime @0x7efea0 (every 5 s, unacknowledged data over 30 s ends the link). Hailstone's own choices, not the original's: a 30 s deadline for the MailLogin reply (the original waits on the link alone), DNS counted inside the 30 s connection deadline, and automatic retries after 5 s doubling to 60 s, at most 5 in a row (the original's ChatServerGiveTime @0x5382d0 drops a lost proxy and waits for the next OP_SetChatServer2; `reconnect_delay` 0 does the same). A link stock UCS closes before answering the login counts as a refusal and is not retried, since EQEmu closes it on a bad key instead of replying. Whether to keep the retries would be settled by how often a stock server drops the chat link mid-session.
- A SessionResponse with the client's connect code is taken from any address and port, and the session moves there. EQEmu binds its UDP socket to 0.0.0.0 and replies without IP_PKTINFO, so a host reached on a secondary or failover address answers from the address its route picks; refusing another address (as the client briefly did) left such servers unable to connect. The cost: the connect code goes out in clear, so someone who sees the SessionRequest can answer first and take the session (and the login that follows) to a host of their own; such an observer can usually forge the server's address as well, so pinning the address would gain little. Whether the original's UdpConnection checks the reply's address is not traced; tracing its SessionResponse case would settle it.
- OP_OutOfSession (`00 1d`) ends the session without a check. EQEmu sends it with a zero connect code, so a check against ours would refuse a stock server's; whether the original's UdpConnection checks anything in it before it ends the link (and with which reason) is not traced. Reading the `00 1d` case of the original's UdpConnection packet handler would settle it. The risk meanwhile: nothing in the datagram is authenticated, so anyone who can forge the server's source address and guess the client's UDP port (a sweep of the ephemeral range) can end a session. Honouring it only when the session is otherwise quiet would close that, but would delay the end of a session a stock server has forgotten (it answers every datagram with `00 1d` and nothing else), so the client keeps EQEmu's behaviour until the original's check is known.
- The link-death timer counts from the last keepalive (`00 06`, taken before its CRC is checked, as EQEmu does) or datagram that passed the CRC and decode. EQEmu's own peer restarts it for any datagram from the address. Whether the original's last-receive time (UdpConnection +0x1d0) is set before or after its CRC check is not traced; reading where +0x1d0 is written in the receive path would settle it.
- A cumulative Ack (`00 15`) whose 16 bits equal the next sequence to send widens to that sequence itself (it is not ahead of it), not 65536 back, so it acknowledges every packet in flight, including ones the server cannot have received yet. That is the original's AckAll (@0x8cdf50: `ack > next` moves it back, `ack == next` does not) and the client keeps it; a stock server acknowledges only what it received, and with at most 400 packets in flight such an ack can only be one 65536 sequences old. Whether the original meant it, or a live capture of an old ack arriving that late, would settle whether to treat it as one behind the oldest instead.
- eqhost.txt: a `Host` line without a port gives the new server the login screen's default port (`ServerProfile::port`, 5997), not one taken from the original; EQEmu's login server takes RoF2 on 5999 by default (docs/protocol/login.md). Which port the RoF2 client uses then, and whether it reads `Host1`, `Host2` and the like as fallbacks (Hailstone reads only `[LoginServer]`'s first `Host`), is not traced; reading where eqmain parses eqhost.txt would settle both (docs/protocol/login.md "eqhost.txt").
- Membership details: the feature ids' names and the refusal lines are decoded (`game/feature_restrictions.h`); the other uses of the 22 entries are not.

## Updates

- A Hailstone folder extracted by hand has no record of what was shipped (`update/installed.txt`), so its first update removes none of the files a release dropped; from the second update on they are removed (docs/updater.md). A file list in the first-install archives would settle it.
- The updater's Windows paths (WinHTTP; renaming the running `hailstone.exe`, `SDL3.dll` and CEF's DLLs into `update/previous/`) are written from Microsoft's documentation and compile, but have not run. A release installed and updated on Windows would settle them.
- Other Hailstone windows on the same folder that the client did not start itself (not the box set's) are not seen when it installs an update at quit.

## Movement and collision

- Collision sweeps and the ceiling query still use a stand-in radius (0.475 x avatar height, 1.78 for a human). Static inspection of the native actor callback resolves an explicit volume override or a model radius with stored scale factors, but the runtime volume selection for player actors remains unverified. `CharacterModel::bounding_radius` has mixed provenance: authored WLD skeleton data, derived static-model bounds, or no EQG value, so it is not a safe substitute. A read-only runtime probe of the native actor's selected volume, override, scale and COFactor would settle this. The existing floor-probe lift and solid-ladder alternatives still compensate for this unresolved radius.
- The swept-sphere geometry (`game/sphere_sweep.*`) remains an independent implementation, with native FPU rounding still approximate. Static inspection settled capsule candidate ordering/counting, axial/tangent branches and parallel edge-region refusal; synthetic float/double regressions cover those choices. The previously reported 12 of 3000 triangle and 73 of 30000 random mismatches describe the older implementation, not a fresh measurement after these corrections. Replaying the external vectors and new targeted recordings would establish the remaining numeric differences.
- The swept sphere's edge-region rule for a path parallel to the triangle's plane (refused: no hit, `sweep_triangle` when `toward == 0`) and the capsule's candidate order and count (cylinder, start cap, far cap; one usable root picks the first, even outside the move) come from a reading of the original's code (SweptSphereTriangle's edge-region selector @0x7a63c0, SweptSphereEdge @0x7a9220), not from its recordings, and the reworked sweep has not been replayed against the recorded vectors (docs/todo.md). Running tests/movement_vectors_test.cpp with `HAILSTONE_VECTORS_DIR`, and recordings aimed at parallel moves and centres inside a capsule, would settle it.
- Collision against other spawns still omits the native bone-attachment geometry (held items); bodies themselves do not block by that static reading. Remote ladder-contact probes use zone and door geometry, not a complete port of actor attachment collision. Hailstone's NPC collision (docs/mechanics.md "NPC collision") remains its own rule on top.
- Vehicles (a design of our own, `docs/mechanics.md` "Boats"): the numbers of the helm's collision (16 probes of radius 1 at the hull's outline), of the rails (a drop over 4 units) and of the hull's refresh (every 200 ms) are ours and were checked only in unit tests, not live against a real dock or the LAUNCH model; a probe already touching something where a step starts is not held by it (so a boat is never stuck), so a hull resting on a dock can be steered through it where only that probe would catch it. Boats the server moves into each other are the server's. A boat a zone script moves riders off is the server's (PEQ drops them at the next zone's dock). With live game files the classic launches and some ships (LAUNCH, race 72 PRE) have no model, so they are drawn as humans and are no boats at all; RoF2's zone `_chr` archives have them.
- The jump's crouch window takes the duck clip's length as its frames x frame time (CAnimation +0x2c was not traced for WLD tracks; a Luclin human's 800 ms gives the 500 cap either way); an EQG clip's is its resampled length (the last key plus one step), not the track's own vf0. The jump animation the still-collision test asks is the renderer's last choice (a frame late at most), and a controlled spawn that is not drawn (first person) counts the 500 ms after a jump as before.
- Frame rate: the game rules run on a 60 Hz game clock (docs/mechanics.md "Frame rate"), so they behave as the original's would at 60 frames a second; whether players ran the original at 60 is not known (it was chosen). With `game.fixed_step = 0` the movement rules run once per drawn frame as the original's code does: a collision hold in the air keeps SpeedZ (a deliberate difference, docs/mechanics.md "Held in the air"; whether the original hung at a jump's top at high frame rates was not tried), and the air friction (0.99 a frame) makes a standing jump reach about 5.2 at 60 frames a second, 4.8 at 144 and 3.1 at 500. Settled by timing jumps and falls in the original at known frame rates.
- Mounts: the camera does not turn about the seat with the mount's pitch.
- Cameras (game/cameras.h): the user cameras' look-at pitch takes CMath's table arctangent (EQGraphicsDX9 0x100b9490), whose tangent-table rounding is not traced (truncated here); the tether camera's start behind the player uses the interpolated table (CMath +0x00 / +0x04, its interpolation not traced: the exact cosine here) and its eye drops to bone 0 while sitting, or for the actor animations 0x21 / 0x24 (+0x10c0), which are not modelled. The camera sweep's filter (0x476410) for actor types 9 and 1 is not resolved: spawns are left out of the sweep. Tracing those functions would settle each.
- Placed objects are triangles of the zone mesh, not separate actors, so actor-only filters do not apply to them.
- Touching switches: the hit callback runs for each door hit in the doors' order, not the DLL's quad tree order. A switch moving into a player who stands still does nothing until the player moves (as the original's standing-still shortcut skips the sweep; not checked against the original).
- Zone points that request a teleport by index send 0xcadf and wait for the server's 0xcadf; EQEmu never sets them, so this is untested. While waiting the player neither acts nor moves but the window keeps drawing (the original blocks the whole client, with no time limit).
- Sense heading's message reads the true heading, not the compass's, and its bands are 64 units wide (225 to 288 is "South", 256 being due south): both as UseSkill @0x45c85f does (checked in the disassembly, 2026-10-29); a negative heading gives an empty direction there too. The compass's own error is ported (`game/compass.h`, checked by unit tests only); which vtable entry 0x65bb80 is (taken as AboutToShow, slot +0xdc: the target is picked when the window shows) is inferred from other windows' tables.
- Position history (OP_FloatListThing): samples are taken at the last good position after a move, before each OP_ClientUpdate, at zone lines, in DoTeleportB and from spells; the samples of the GM and server teleport handlers (OP_Translocate, the rez, opcode 0x4fd9, HandleWorldMessage's reasons 5 and 7), the camera's (`CRender::LocalViewSetup`) and the vehicle-relative sample are not taken, and the send when the local player is created goes nowhere (the samples are only forgotten).
- A window close request on a loading screen waits for the next screen (as the original's queued message would); a second one quits at once.
- Which zone version the server runs: RoF2's zone-in packets do not say, so with a live asset folder and no `.s3d`, the revamped `.eqg` of bazaar, highpasshold or lavastorm loads only when the safe point OP_NewZone sends stands on its floor (at most 10 units above it; game/revamped_zone.h). It was measured on PEQ's rows only: the revamp's safe points stand 2.0 to 4.2 units above its floor, and the old versions' have no floor under them (bazaar, lavastorm) or one 15.9 units down (nektulos). A server whose zone row has another safe point (an unset 0, 0, 0, a point in the air) gets the refusal or, by chance, the revamp. There is no fallback on the spawns: they arrive after the load has started, so testing them would mean loading the zone twice. A neighbour zone loaded ahead (no OP_NewZone yet) and the offline viewers keep the refusal. Testing other servers' zone tables would settle it.
- Arena and Nektulos with a live folder: the `.s3d` wins over the revamped `.eqg` (`is_eqg_zone`), as before, and the safe-point test is not asked. Yet PEQ runs the revamp there: its only Arena row's safe point stands 4.2 units above the live arena.eqg's floor and 51 above arena.s3d's, with 6 of 6 spawns on the `.eqg` and 1 of 6 on the `.s3d`; Nektulos version 1 (expansion 10 on) has 400 of 404 spawns on nektulos.eqg and 39 of 404 on nektulos.s3d. Whether a RoF2 folder's own arena.s3d and nektulos.s3d are the live folder's, and whether the safe point should also choose between a present `.s3d` and the `.eqg`, are open. Comparing the files with a RoF2 install would settle the first.
- The local player's fly mode (docs/mechanics.md "fly mode"): the original rebuilds its effect cache, and so recomputes levitation, whenever something clears the cache flag (+0x1a4): OP_Buff in every form, `HitBySpell`, `RemoveAffect`, the buff tick for tick-varying effects, and possibly worn item changes. Hailstone counts a change of a buff slot's spell (or of the SPA 57 values) as a rebuild, so an OP_Buff that refreshes a slot with the same spell, the tick and an item change do not put a server-set mode back; a slot losing or gaining a levitate spell stands for `RemoveAffect`'s and `HitBySpell`'s SPA 57 cases, though OP_Buff's copy (bufffade 3) calls neither; the "no levitation left" test reads the buff cache's SPA 57, where `PlayerZoneClient::Levitating` also counts worn items and AAs. At zone-in Hailstone applies the spawn record and then rebuilds; whether the original's first rebuild comes after its own spawn exists (`UpdateLevitationState` does nothing without one) is not traced, and only matters when the record disagrees with the buffs (stock EQEmu sends 2 for a levitating player, else 0). A live session with GM `#set flymode` and buffs, or a trace of the cache flag's writers, would settle it.

## Navigation (a Hailstone addition, docs/navigation.md)

- Find's navigation line and rainbow strands use the static zone collision, with synthetic geometry tests and offline GPU previews. Live readability, winding stairs and moving platforms still need acceptance in the client; a moving platform is not part of this ground query.
- The navigation mesh's agent (height 6, radius 2, climb 4, slope 55 degrees) is chosen, not taken from the original, which has no navigation; the movement sweep's own radius is itself a stand-in (above). Paths keep wide of walls so the sweep does not catch; a narrow passage the sweep fits through but the mesh does not is left out. Settling the sweep radius would let the agent match it.
- Navigation links (docs/navigation.md "Links"): the safe drop (20) is ApplyFallDamage's for a character carrying nothing, falling from rest at the default gravity in continuous time; weight shortens it (a heavily loaded character takes a little damage from the longest drops), the zone's gravity can differ, and the physics' own steps were not simulated for it. The climb of 4 is read from the sweep's lift, not measured per race (a gnome's lift is smaller). How high a ledge the swim jump climbs out onto (5), the spacing of links (5 along a ledge, 15 between swims) the steep swim pitch (80 degrees) and how far on along the path a swimmer aims (4), and the strafe's ledge test (4 to the side, a drop over 5) are ours. Jumps up onto ledges and lifts are not linked. Walked in Old Sebilis by the movement rules offline (no monsters, no breath); not yet tried live.
- Stacked floors (docs/navigation.md "Floors over floors"): a corner or the end counts as reached within 8 in height, and a goal's floor is chosen with height weighing four times distance across. Both are our own numbers; floors closer than 8 apart could still be confused. Not yet tried live.
- A walk clicks a closed door it stalls in front of. RoF2's door record has no teleport destination (the server decides on the click), so a door that zones the player cannot be told apart and would be clicked too; `/nav option doors off` stops it. Not tried live.
- Swimming (docs/navigation.md "Water"): the surface is meshed and the walk steers the look pitch; when to head for air (35%), how near a shore to climb out (12) and the steepest pitch (63 degrees) are our own numbers, and it has not been seen live end to end. Levitation is not navigated.
- /follow's mesh help (a deliberate change, `nav.follow`): its 400 leash and 5 s rest after a stuck detour are our own numbers. Not yet tried live.
- Replies to `/find` and the navigation's quiet path request carry nothing to tell which request they answer, so the client gives each to the oldest request waiting. Stock EQEmu sends an empty or partial route at once but a full path from a thread-pool task (`Client::SendPath`, `SendPathPacket`), so a quiet request for a long path and a shown find that fails just after it can swap: the navigator gets the empty route and the find draws the navigator's path. A request unanswered for 10 s (a client number) is taken as never answered; a server that stalls longer leaves every later reply one off. Not seen live. Not sending a quiet request while a shown find waits (and the reverse), or checking a reply's end against the requested spawn, would narrow it.
- Seen live on the NMS Dev server (East Commonlands, 2026-11-01): the build and cache, walks to points and to a door, /moveto, the TLO, the overlay, pause, a player key ending the walk, a walk to unreachable ground. Not yet seen live: following a moving spawn, a closed door clicked on the way, the server's /find path while the mesh builds.

## Combat, abilities and spells

- Leadership purchase costs: the client shows RoF2's native progression (constructor `0x55d8e0`, next-cost getter `0x561750`): group Mark NPC costs 3/4/5 and raid Delegate Main Assist (index 19) costs 6/7/8. Legacy EQEmu `zone/aa.h` charges 1/2/3 at index 0 and 6/6/6 at index 19. The purchase packet carries only the index; the server decides the actual charge and returned points. There is no cost-table packet. A server-provided cost table or an explicitly selected compatibility policy is needed to make the displayed estimate match every server; the current client keeps native costs.

- Leadership stat display follows the native effects: HP regeneration adds 1/2/3 per active group/raid rank and offense adds 7/15/22/30/37. Legacy EQEmu applies 4/6/8 and 10/19/28/34/40 server-side instead. The protocol supplies ranks, not a bonus table. Received vitals and server combat remain authoritative; a server-provided effects table would be needed to match arbitrary server tuning in the local calculations.

- Blood rendering now resolves the exact WLD `<code>_BLD_DAG` and the player's `I_BLOODSPRITE` resource. Missing authored bones, multi-frame sprites or unsupported materials omit it; new-style actors have no blood attachment in the checked native setup. The synthetic fixtures establish plumbing, not live appearance or native random-table parity.
- Tracking and ranged auto attack are not modelled in the death report.
- Hover respawn follows EQEmu's RoF2 packet lifecycle and has loopback and physics regressions. Exact native death-camera transitions have not been traced: the current view stays while dead, with the existing unconscious-camera restoration and death music stopped on same-zone recovery. Live bind, ordinary/Divine resurrection and controller acceptance remain to be checked against a server, including cancellation of a pre-death isometric click-to-move interaction at same-zone placement. ConfirmationDialog_HandleResponse @0x52d540 case 0x67 holds a yes back from OP_RezzAnswer only when the offer's corpse name (+0xa0) also matches the local player's name; what the local player's name is while hovering on EQEmu was not checked, so the client compares only the zone dword (a mismatched name would be held back here where the original answers at once). Settled by reading the local spawn's name during a live hover with a resurrection offer.
- A spell whose casting animation (spells_us.txt field 120) is 0: when Hailstone's added proc cast stage plays it, the option `cast_animation_fallback` (on by default) plays 43 for a beneficial spell and 44 for a detrimental one. The original's EQPlayer::TriggerSpellEffect (@0x593d10) passes the spell's +0x274 to the source's animation as it is, 0 included; what action 0 shows on a model, and how many stock spells have it, was not checked. Settled by landing such a spell (a weapon proc) on the original client and watching its source.
- Valid spell missile lifetimes, stages, area contacts and special spell 54/859 endings are implemented from checked behavior. The large-source launch point uses only a real posed role-0/name anchor; without one the packet origin is preserved, a deliberate safe difference from the native unchecked temporary. Recorded vectors and live server acceptance are still missing.
- Spell particles, what the DLL's particle update reads from the actor and the creator: the actor's world matrix (vtable +0x2c4) gives a spell emitter's axes as they are, normalised here: whether its rows carry the actor's scale was not read, and the client applies that scale once, through the root actor's GetScaleFactor (taken as the spawn's model scale, +0x31c). The actor's GetAlpha (vtable +0x208, its point's +0xac / +0x80 getter) scales the particles' opacity; the renderer fades no actor yet, so it is 1 in play. An actor's own emitters (CActor::vf126 @0x1003a950, the DLL's own caller of the creator) take the moddat.ini PESFactor of the point's actor. An entry with the floor flag (.prt +0x5c) is made on the floor below its point (a sweep down, + 0.05) with the actor's matrix and no point, so it does not follow the actor: what makes it again as the actor moves was not traced, so the client keeps it on its point, following the actor. The emitter-scaling radius that scales their shape and counts (spawn +0x1220) is -1 from stock EQEmu, so they are not scaled. +0x178's orientation angle (a column of the attachment's matrix projected on the screen) is not drawn; the DLL's random tables (filled at run time) are replaced by this client's generator; whether particles pass the alpha test (ALPHAREF 1, its compare function not set by the particle render state) is not known, and none is done. The animation-started entries' timing is an approximation (docs/formats/particles.md). Settled by tracing those callers and run-time reads in the original client.

## World rendering

- Sky: the classic sky layers are drawn, not a procedural sky. - Fog: the area fog distance blend and the weather fog band are not applied; lightning fog is not applied. The area fog needs `weather.ini [AreaFogSettings]`, which neither the RoF2 nor the live install has, so it shows nowhere. The modern lighting has its own: the haze eased between places, a storm fog band and the lightning in the haze (docs/graphics.md, Modern lighting).
- Lighting: multi-pass point lights are summed per vertex; the player's light level, the lighting of EQG materials, doors and characters, and placed objects without colours are approximations. In the classic lighting the characters take the region shaders' scene light with the zone's baked light where the player stands as their vertex colour, never below 0.25 (docs/graphics.md); the original's skinned-model shaders (`SkinMeshOld` and the rest) compute their `lit` some way not traced. Settled by reading the vertex shaders' constant use in `RenderEffects/SPL/SkinMesh*.fxo` and what `CRender` binds to them.
- EQG: the RegionLava2 and RegionLavaH formulas are not settled (the modern lighting draws both as its own lava); the sidecar's second line is taken as ms a frame and its count wins over a longer list (chambers' ra_blood01_n_001.txt says 9 and lists 10); alpha-test references of water effects, normal/environment/glow map use in the classic look and the heightmap lighting colour are approximations. A heightmap tile without ecosystem layers takes its nearest painted neighbour's base ecosystem (the original draws none). The zone line boxes of toxxulia, mistythicket and oldbloodfield lie 200 to 600 below the ground, read as the original reads them (docs/mechanics.md, "Heightmap zones' ATP boxes"), so the original never crosses their zone lines. These files are newer than RoF2, and how later clients place the boxes is not known. The client works around it with its own fallback (docs/mechanics.md, "Buried zone lines": a box with ground well over it and no floor at its depth fires from the ground over its footprint), which is not the original's behaviour. On the server side, EQEmu's virtual zone points (`is_virtual`, not set on the test server) would make the lines usable.
- EQG winding: EQG triangles are treated as counter-clockwise front faces (found by testing).
- WLD: placements with Z = -32768 are loaded as stored; the placement tilt sign is negated (as EQEmu's azone does); bitmap names that exist in both a zone archive and its object archive are read from each WLD's own archive. User-defined render methods 0x8000001b–1d and 0x8000002a and up are not in the DLL's legacy table (CRender::InitLegacyRenderMethodTable @0x1009aa40 stores 0x00–0x29, skipping 0x1b–0x1d), so what ResolveTransparency reads for them is not known; they are drawn opaque, except the untextured 0x8000004b and 0x80000053, which stay invisible (only 0x80000031, gequip's PIPE-MOUTH, ships). Settled by reading what lies at CRender +0x238c past the table, or by the original drawing that pipe.
- Detail textures, radial flora exclusion areas and the flora's exact density rules are partial. The flora's bounds against damaged `.eco` files (`*ITERATIONS` at most 10,000, `*DENSITY` at most 100,000, 65,536 plants per tile and ecosystem; the game's files reach 500 and 2,800) are Hailstone's: how the original takes larger values is not traced.
- A WLD palette map (detail textures) stored top-down (negative BMP height; none ships) is flipped so v = 0 stays the picture's bottom row; whether 0x10019780 reads such a file in storage order is not traced.
- Mip filtering: Hailstone builds a mip chain for a world texture that ships without one in linear light (`assets::build_color_mips` on the CPU, or the GPU's blit on an sRGB view for an opaque power-of-two image, which comes out the same; docs/graphics.md). How the original made the chain for such a texture (by hand, D3DX, or hardware generation, and in which colour space) is not traced; reading its texture setup would settle it. A cut-out's chain is a client rule of its own (alpha-weighted colour, level 0's coverage kept on every level) and the original's cut-out mips are not traced at all.
- A compressed texture (BC1/BC2/BC3) that ships with its own mips goes up compressed where the device supports BC. One that ships without mips, or a BC2/BC3 painted on a colour key, is expanded to RGBA8 for its chain (the colour key taken out) and uploaded uncompressed, four to eight times the texture memory of the compressed form: Vulkan's blit cannot filter a compressed format, and the client has no BC encoder to compress the chain again. The original kept its DXT textures compressed; how it handled a mipless one is not traced.
- harbingers' BCN door (BCN.MDS, an EQGS model) is drawn in its bind pose with its first piece (OBJ_beacon0200 of
  three). The archive loader (0x10066230) hands every member to EQG_LoadFileByMagic @0x10065c00, which loads EQGS
  (0x100631e0) as it loads EQGM (0x100624e0), so it is taken to register `BCN_ACTORDEF` as the .mod models do; the
  name, the piece the actor shows and whether it plays bcn_default.ani were not traced. The NMS server does not send
  that door, so it was not seen live.
- Zone bounds for the map use the collision mesh.

## Audio

- Reverb is simplified (no Miles DSP); music synthesis uses TinySoundFont rather than a DLS synthesiser, ignoring sysex and branch controllers.
- Duplicate sound names across archives resolve to the highest-numbered archive.
- A NaN or infinite volume, level, send or reverb parameter (an EMT gain of "nan" read with strtof) is 0, and a non-finite sample (an IEEE-float WAV's) is silence; what Miles does with them is not known. Ours: they would otherwise stay in the reverb for the session.
- Decoded waves not asked for over two zone changes are freed (`SoundLibrary::drop_idle_waves`; the global waves stay), so a freed wave's next play is skipped while it decodes again, as any wave's first play is. The original's wave cache policy is not traced.

Settled by reading that query, or by pressing Tab in the original client with an NPC behind a wall.

The HP gauges' `PlayerZoneClient +0x194` test (the pink band) is not known.
- The modern pack's hot bars lay out vertically by their own "Buttons per row"; the stock window's vertical page buttons (`HB_VerticalBarPageButtons`) stay hidden in the model. The gamepad pack's bars turn vertical (a column left of the minimap, the buttons smaller when the screen is short) by a click on their page number, kept as its own setting `hotbar.vertical.<window>`; with Show Spinner off there is no page number to click.

- The Find window's quest givers (server/README.md) are the NPCs whose own quest file has a say or hand-in handler, by the file's text: a handler a Perl plugin or an encounter adds at run time is missed, and a file that has the handler but does nothing in it is counted. Two NPC types with the same name in a zone, one of them scripted by id, both show as having quests. Asking EQEmu's own `HasQuestSub` from Lua (not exposed) would settle it. - Context menus and the EQ menu use this client's own style; the cursor attachment's placement is approximate.
- Windows scale with the display scale; sizes are stored unscaled.
- Escape and the UI pack's windows: the modern pack's windows close on the close-top-window key only when "Close with Esc" is ticked in their right-click menu (on by default for the windows opened to look at something, listed in `lib/escape.lua` DEFAULT_ON; off for the rest), the frontmost by the order they were opened or clicked. Which of the original's windows close on Escape, in which order, and whether it then also clears the target, is not traced (CLOSE_TOP_WINDOW in `__ExecuteCmd` and the window manager's escape handling would settle it).
- File selection browses folders, not the OS shell namespace.
- Context tips: the event tips are hooked (experience, group and guild invitations, consent, red con on the attack key and on a target change while attacking, world containers, interactive objects, the Actions window's page on show, player customization), unit-tested; EQEmu never sends the experience tip's flag (the second dword 2). Not hooked: the Actions window's page keys while it is already shown (0x614510's other callers) and its Abilities page function 0x613a20, the Options window's Display / Keyboard pages (COptionsWnd::WndNotification, 6 / 7), the hot bar help (CHotButtonWnd::WndNotification, 0x57 forced), the merchant tips 0x25 / 0x30 / 0x3f (0x4107d0, 0x5aa200, 0x460b40: their callers not traced) and the real estate overview key (0x51: the overview window is not built).
- `/report` text collection, `/outputfile` destination (the character's folder) and `/survey` (shows the address) differ in detail.
- Slash-command numbers (`/split`, `game::cmd_atol`; and every other atoi of typed, server or text-file numbers in `game/`, `core::msvc_atoi`): the original's atol on its 32-bit long; the client accumulates the digits in 32 bits and wraps, as the port's MSVC atoi does (`spell_description.cpp`), and `/split` sums the four amounts with a 32-bit wrap. Whether the CRT the original links wraps or saturates (LONG_MAX) a number out of range is not traced; only `/split` amounts past 2147483647 differ. Reading the atol / strtol the original links would settle it.
- The chat log (/log): the client keeps the file open while logging and writes each line through at once; whether `CEverQuest::OutputTextToLog` @0x5130c0 opens and closes the file per line, or holds it, is not traced. The difference shows only when the file is moved or deleted while logging: on Linux and macOS the lines then go to the removed file until `/log` names a file again or is turned off and on (on Windows the open file cannot be deleted). Reading OutputTextToLog's file handling would settle it.

- `mq.event` (`mq/event_pattern.h`, MacroQuest's Blech read as the spec): a `#n#` used twice in one pattern hands on its last; LuaEvent sorts the values with `std::sort`, which MSVC runs as an insertion sort (stable) for up to 32 values, so that holds for up to 32 `#...#`, and past that the order MSVC's introsort leaves them in is not traced. Patterns that share a literal's beginning are matched each on its own (Blech's shared tree can turn down a line one of them alone would match: a deliberate difference). Running a script with such a pattern under MacroQuest would settle the first.

## Scripts (MacroQuest's TLOs)

- `Math.Dec` past 32 bits (`${Math.Dec[123456789ab]}`) is held at 0xFFFFFFFF (-1), as strtoul does; MQ reads it with MSVC's `sscanf("%x")`, whose result there is not checked, and a blank-only index (where MQ's sscanf returns EOF and MQ uses an unset value) is NULL here. Running those two in MacroQuest on Windows would settle it.
- `String.Compare` and `CompareCS` give -1, 0 or 1; MQ returns `_stricmp` / `strcmp` as they are, whose size (beyond the sign) on MSVC is not checked. `${String[abc].Compare[abz]}` in MacroQuest would settle it.

## Server-specific extensions

- Ability Book class filter on an NMS multiclass server: the server sends every AA one of the character's classes may use with the class mask 0xFFFFFFF (zone/aa.cpp, the AA rank packet), so the book counts all of them as Shared and a class filter or the class sort cannot tell them apart. Only the AA's real mask, from the server or the AA tables, would settle it. Skills get their classes from the skill cap table at the character's level, and combat abilities from the spell's class levels.
- Autoskill's "only when its buff has worn off" looks for the ability's own spell id among the player's buffs. An AA or combat ability whose spell only triggers another spell (the buff then carries the other's id) is never seen as buffed, so it is used again whenever its reuse timer allows. The spell's trigger effects (SPA 340, 374, 470 and similar) would settle which id to look for. Its "out of combat" trusts the server's OP_RestState flag, which EQEmu sends only while rest regen is on (`Character:RestRegenEnabled`); without it, out of combat is only "auto attack off".
