# Character models (WLD, Luclin, EQG) and appearance

Implementation: `src/assets/character.{h,cpp}` (archives, models, clips), `src/assets/character_dress.cpp` (appearance: armour, faces, helms, robes, tints, held items, Luclin layers and parts), `src/assets/eqg_character.{h,cpp}` (EQG models), `src/game/appearance.{h,cpp}` (which value drives which part, OP_WearChange), `src/game/race_models.{h,cpp}` with the generated `race_models.inc` (`tools/gen_race_models.py`), `src/render/actor_renderer.{h,cpp}` with `shaders/actor.{vert,frag}` (GPU skinning, tints). Tools: `chrdump` (`--luclin`, `--names TEXT`), `hailstone --model` (appearance per model, `--dress`, `--luclin`). Tests: `tests/character_test.cpp`, `tests/appearance_test.cpp`. Fragment layouts are in `docs/formats/wld.md`.

Credits: clip assembly, donor clips, rigid skinning, the bottom-up character BMP rows and +X as the model front follow OpenEQ (MIT OR Apache-2.0, `src/assets/character.cpp`, see `THIRD_PARTY.md`); which models borrow clips comes from LanternExtractor's (MIT) `animationsources.txt`, copied to `tools/data/lantern_animationsources.txt`.

The numbers below come from a RoF2 install (2026-10-20).

## Archives and load order

`global_character_archives()` follows the client's start-up order:

1. `Resources/GlobalLoad.txt` (`phase,?,flags,file,text`), phases 1 to 4 in file order, keeping the entries whose file contains `_chr` and is not an `.eqg` (globalfroglok, globalske_chr2, ske_chr, the 3rd-phase NPC archives, global6/4/_chr, global2/3_chr ...).
2. `global5_chr` and `global7_chr`, which the client loads next to the Luclin models, then the extended armour textures `global17_amr` … `global23_amr` (`Global%d_amr`, textures such as `HUMCH1701` for materials 17+).
3. `Resources/GlobalLoad_chr.txt` (`count`, then `code,file`): S3D entries only. When the code and the file share their first three letters (`cwr,cwr`) the file is an EQG.

Per zone, `zone_character_archives()` adds `<zone>_chr2`, `<zone>2_chr`, `<zone>_chr` and the S3D entries of `<zone>_chr.txt`. Every WLD in each archive is validated, but only a compact resource index is retained until first use. The first definition of an actor or track name wins. Shipped: 52 global archives with 182 actor definitions, parsed in about 0.4 s; the app keeps them between zones (`CharacterArchiveCache`).

Storage: a character archive in the asset folder (or the classic folder) is mapped read-only (`PfsArchive::open` with `PfsArchive::Storage::Mapped`, decided by `PfsArchive::storage_for`; `platform::MappedFile`) instead of copied into the heap, so only the archive index (`names_` and `by_name_`) is private memory and the bytes live in the file cache, shared with other readers and evictable under pressure. An archive from a server's overlay (`servers/<id>/assets`) is read into the heap as before: the server files sync replaces those files while the client runs, which Windows refuses for a file with a mapped view (docs/hardening.md "Mapped game archives", also for what a game file truncated under the client does now). `from_memory` keeps its owned buffer, and both parse through `ByteReader` over the same span. `CharacterArchiveCache::clear()` lets the old archives go on an asset-folder or overlay change. Character tables store WLD objects and positive fragment references, and copy the small track-reference records needed for clip lookup. `WldFile::deferred` validates one complete WLD at a time, retains only successfully decoded named actors, meshes, materials and track references in original order, and drops the decoded payload. First payload access inflates and parses that WLD again from the same archive. Decoding is synchronized and shared across copies; public character build/dress/material operations acquire `WldFile::ReadScope` leases. Nested calls share the outer lease, and exceptions end leases too. When the last concurrent lease ends, the decoded payload is not dropped at once but kept in a process-wide retained set, least recently released first out, while the estimated decoded bytes (`retained_bytes()`) of all retained WLDs stay within `WldFile::kDefaultRetainBudget` (128 MiB; `WldFile::set_retain_budget`, 0 drops payloads as the last lease ends). The next lease takes a retained payload back without decoding: building one model after another from `global_chr.wld` (each a cache miss of its own, on the frame thread or the dresser's) decodes it once, not once per model. The set is not emptied on a zone change: the global archives stay loaded between zones and the budget bounds it, and a zone's own archives leave it when they are destroyed. An unscoped raw WLD access pins its decoded data for the WLD lifetime, preserving direct callers that hold fragment pointers. Ordinary zone WLDs remain eager and are not reclaimed this way. The validation pass still incurs one WLD's transient decode cost; this reduces retained memory, not the amount of initial validation work. Model enumeration in tools may intentionally materialize every actor's WLD. `CharacterArchive::archive_bytes()` / `owned_bytes()` / `parsed_bytes()` (and `wld::WldFile::retained_bytes()`) count the two separately; the historical 926 MB archive increment is not re-measured here and is not all archive bytes, so the mapping alone does not claim it back.

The app also keeps what was built from the global archives alone (`SharedCharacterCache`): models, appearances and item models, each with the names its build looked up in the library's tables (`CharacterLookups`: actors, tracks, clip lists, meshes, files, Luclin materials and parts). A zone's library takes an entry only when its own archives define none of those names, so a zone's override of a global model, track, mesh or texture never comes from the cache, and what a zone's archives changed never goes into it; appearances are keyed by the shared model object they dress. The renderer keeps the meshes and textures it put on the GPU for those across a zone change (`ActorRenderer::release_kept`, read again when the new zone's archives define a name a texture looked up). Both keep only what was used in the zone just left. Measured with the live asset folder: building and dressing every global model in The Bazaar took 1.0 s the first time and nothing the second; after The Bazaar, The Plane of Knowledge shared 177 of its 204 models and built the rest in 0.12 s. The global archives' name tables are built once too (`CharacterArchiveIndex`, again after `clear()`: another asset folder or server overlay) and every zone's library shares them; it indexes only its own archives, on top: a name its archives define goes on from the global tables' state (resource levels, clip lists), so it resolves exactly as one library over all the archives would. A zone's library took 0.65–1.0 s to make with the live asset folder and Luclin models (the global archives indexed again each time); with the shared index it takes 20–45 ms (The Plane of Knowledge 50–100 ms), reading and indexing the zone's own archives.

The GlobalLoad.txt entries whose flags' fifth letter is `E` (equipment: `gequip*`, `frogequip`, `global_obj`, `loyequip`, `ldonequip`, `gatesequip`) are loaded too; they hold the `IT<n>_ACTORDEF` item models. With Luclin models on (the app always asks; eqclient.ini decides), `luclin_character_archives()` reads eqclient.ini `[Defaults]` `AllLuclinPcModelsOff` and `UseLuclin<Race><Male|Female>` (default TRUE; race names: Human, Barbarian, Erudite, WoodElf, HighElf, DarkElf, HalfElf, Dwarf, Troll, Ogre, Halfling, Gnome, Iksar, VahShir) and loads `global<code>_chr2.s3d`, `global<code>_chr.s3d` for each enabled code plus the part archives `lgequip`, `lgequip2`, `lgequip_amr`, `lgequip_amr2`, between GlobalLoad phases 2 and 3. Since the first definition wins, the Luclin `HUM_ACTORDEF` then replaces global_chr's. With all of them, 122 global archives parse in about 0.75 s.

EQG models are not in these archives: see "EQG models" below.

## Model

`<CODE>_ACTORDEF` (0x14) → 0x11 → skeleton 0x10. Example, HUM in `global_chr.wld`:

- 25 nodes. Each names a 0x13 track (`HUM_TRACK`, `HUMPE_TRACK` pelvis, `HUMTH_R_TRACK` ..., `HUMR_POINT_TRACK`, `HUMHEAD_POINT_TRACK`, `HUMSHIELD_POINT_TRACK`). The parent of a node is the node whose child list holds it; a bad index, two parents or a cycle rejects the model.
- Frame 0 of each node's own track is the rest pose: local = T · R · S (quaternion normalised), model = parent · local. The rest pose is a T-pose about 6.7 units tall with the origin about 3 units above the soles (HUM z −3.00 … 3.67).
- Meshes are the skeleton's mesh list (flag 0x200): `HUM_DMSPRITEDEF` (body, 669 vertices) and `HUMHE00_DMSPRITEDEF` (head, 122 vertices). Without the flag, each node's sprite is used and a mesh without vertex pieces follows its node.
- Every vertex belongs to one node through the 0x36 vertex pieces `{count, node}` and is stored in that node's space, so skinning is a single bone matrix per vertex. No inverse bind matrices.
- Materials come from the mesh's palette, grouped per render group like zone meshes (`wld::build_mesh`). The palettes also list robe (`CLK04xx`) and helm materials that the default render groups do not use. HUM's materials are `HUMCH0001` chest, `HUMLG000n` legs, `HUMFT000n` feet, `HUMUA0001` upper arms, `HUMFA0001` forearms, `HUMHN000n` hands and `HUMHE000n` head, nearly all render method 0x80000014 (opaque). The texture number encodes variant and part (`HUMCH0001` = chest, variant 00, piece 01).

Character BMPs are stored bottom-up relative to the model UVs, so the renderer flips the rows of BMP files (not DDS files, even when named `.bmp`). Without the flip faces and chests are upside down.

The model front is +X (HUM's toes are at +X once the pelvis' 90° turn is applied). The model is placed with T(position) · Rz(heading_to_yaw(heading)) · S(scale), using `game/coords.h`'s heading, which is 0 = +X, counterclockwise.

## Clips

An animation clip is a set of 0x13 tracks named `<clip><bone track>`, for example `L01HUMPE_TRACK`. A clip code is a letter and two digits:

| Code | Use |
|---|---|
| L01, L02 | walk, run (L03–L09: jump, fall, crouch-walk, climb, swim ...) |
| P01 | stand (passive); O01–O03 idle variations |
| C01–C11 | combat (kick, pierce, slash, bash, ...) |
| D01–D05 | damage; D05 death |
| P02–P08 | sit, stand up, crouch, ... |
| S01–S28 | social emotes; T02–T09 spell casting |

The library indexes every track whose name starts with a clip code by the rest of its name (the bone track), so a model's clips are found from its bone names. For HUM, `global_chr.wld` holds only L01, L02 and P01 (24 of the 25 bones each; the root is not animated); everything else is borrowed:

- A model borrows from a donor model listed in LanternExtractor's `animationsources.txt` (HUM, BAM, ERM, HIM, DAM, HAM ... → ELM; HUF ... → ELF; TRM, TRF, OGM → OGF; HOM, GNM → DWM; ...). The donor's bone track is the model's with the code replaced (`HUMPE_TRACK` → `ELMPE_TRACK`). The RoF2 client's own list (`ActorAnimation::GetAlternateAnimTag` @0x406a60) names some donors Lantern's leaves out; its unconditional three-letter ones are added from `tools/data/rof2_animation_sources.txt` (the female froglok FRF → FRM, whose archive holds FRM's tracks only; SHF → SHM, WAF → WAL, KES → KEM and others). Its two-letter prefixes are not taken over; the choices its `flag` makes are in the next item.
- A clip for which the model has at least one track of its own uses only its own tracks; otherwise the whole clip is borrowed (OpenEQ). Bones without a track keep their rest pose.
- A Luclin player model (one with a `TUNIC_POINT` bone: the original's InitAnimationTracks @0x407800 asks for the `TUNIC_POINT_DAG` and passes whether the actor has it to `GetAlternateAnimTag` as its `flag`) takes other donors for some codes (`game::animation_source`): HU* and ER* take the human's clips (ERM → HUM, ERF → HUF; HUM and HUF none but their own), BA* none but its own, SKE HUM's. Every other code takes Lantern's donor (HIM, DAM, HAM ... → ELM). With the wood elf's clips a Luclin erudite's face bones took the elf's places (lips parted over the teeth, brows in a frown) and its `BEARD_POINT`, for which the elf has no track, stayed at its rest place in front of the mouth, so the beard part hung there; the human's clips key both where the erudite's own face has them.
- A track lends only to its own skeleton. A track in another WLD that defines the same code with a different skeleton is not the model's: live's `wol_v2_chr` WOL shares the root and point names with the classic WOL. A borrowed clip is lent only when at least one of its tracks is in a WLD whose own donor skeleton has an equivalent of at least half of the model's bones (or that does not define the donor): global_chr's classic ELF shares only the root, PE, CH, NE and HE with the Luclin ELF, and without this rule a Luclin human, high elf, erudite and others got C10, C11 and T07..T09 from it, with every other bone in the rest pose, and threw or kicked in a T-pose. Zone models with a classic skeleton (Coldain, Kerran, Iksar skeletons and others) likewise lose the clips they took from a Luclin donor's few shared bones. Among the global and Luclin models only such clips go (every one of them left at least 80% of the bones at rest); no clip that stays changes.
- Frame time: the 0x13 frame time (flag 1) of the first multi-frame track, otherwise 100 ms. All classic clips use 100 ms except T08/T09 (50 ms). The clip length is the longest track. Shorter tracks wrap.
- Sampling interpolates between frames: slerp for rotations (shortest path), lerp for translation and scale. Looping clips wrap; the corpse pose (D05) holds its last frame.

HUM with all global archives has 71 clips: L01 12 frames, L02 12, P01 9, O01 49 (borrowed), and so on. Newer models use a fallback race for missing tracks (`<anim>_<CODE>` retried with HUM → 522); that is for the newer, Luclin-style track names and is not used for the classic clips.

### Animation key storage

`AnimationTrack` shares key arrays between copied clips and models; builder mutation detaches before changing keys. Luclin base/take aliases keep their existing clip entries, precedence, frame count, frame time and borrowed flags, while their key arrays are shared. WLD and EQG builders reserve their known frame counts instead of growing each key array geometrically.

After construction, `CharacterModel::compact_animations` interns bit-identical tracks within that model. There is no global interning table retaining entries across zones. A constant track stores one physical key but keeps its original logical length: sampling still applies the original loop period and the multi-key interpolation/normalization path. Float components are compared by bits, including quaternion signs and signed zero; no approximate pose merging or precision reduction is used. Copies of compacted tracks expand their repeated keys before mutation. This affects storage only, with the original clip lookup and sampling rules retained.

Model memory estimates count physical key arrays once within a model, and cache snapshots count them once across all visited models. Per-model estimates therefore cannot simply be summed when copied models share key storage. Track wrapper arrays and heap vector objects are counted, while reference-count control blocks, capacities and allocator overhead remain outside the estimate. Runtime savings and loading costs still need a fresh build and route comparison.

## Luclin models

A Luclin model (`HUM_ACTORDEF` in `globalhum_chr.wld`) is a WLD skeletal actor like the classic ones, with 104 bones (face bones, `HAIR_POINT`, `BEARD_POINT`, `HEAD_POINT`, `TUNIC_POINT`, `CHEST_POINT`, `SHOULDL/R_POINT`, `GAUNTL/R_POINT`, `LEGL/R_POINT`, robe bones) and one body mesh.

- Clips: track names carry a fourth letter, the take: `C01AHUMPEBIP01_TRACK`, `L10BHUM…`. The library indexes `<code3>` and `<code4>` readings; a model plays `C01A` (else `C01B`) as `C01` when it has no animated `C01` of its own (OpenEQ's alias rule). The `_chr2` archives hold the takes. The take is the holding column (`InitAnimationTracks` @0x407800 binds a tunic-point model's A..H to columns 0..7): `PlayerClient_UpdateHoldingAnimation` @0x58d780 gives a spawn holding nothing column 0 (A) and one holding anything in either hand 1..7 (3 with both hands), and `0x4b1210` takes column 1 (B) for a column the model has no take of; no model ships C..H. So a Luclin model holding something plays its B takes (`CharacterModel::held_aliases`, `clip(code, holding)`, `game::holds_item`): the Dark Elf female's P01B carries the shield arm about 0.36 units higher than P01A, where it hangs.
- Materials are palettes of layers: `HUMCH0001_MDF` names a bitmap whose file list is the skin (`humchsk01.dds`) and an armour layer with alpha (`humch0001.dds`); a `_LAYER` suffix on a name is dropped. They are drawn as: `lerp(t1.a, t1.rgb × Tint.rgb, t0.rgb)`, lit after; `Material::tint_layer` is the second texture. Heads: the material is `<code>HE<selector><piece>_MDF`, the selector 0 (Erudites: the hair style, scalp glyphs; Barbarians: face / 10) and the face the piece's tens digit (`HUMHE0011`), as OpenEQ names them; the face is swapped in as the original's SwapFace does (`game::swap_face`, `game/actor_look.h`). Only the Luclin model WLDs, `globalpcfroglok_chr` and `*_amr*` WLDs are searched.
- Dressing (`game/actor_look.h`) runs over `assets::DressEnv` (`character_parts.cpp`), which stands for the model: first the body materials for slots 1–6 from material 0 (replace `<code><part><mm>01_MDF`, more passes for the piece digit; Vah Shir and Froglok `<code><part><mm><v>1_MDF`), then the facial features (hair `IT<1000 + style + offset>` on `HAIR_POINT`, beard `IT<2000 + …>` on `BEARD_POINT`, Vah Shir (face ≠ 7) and Froglok `IT0` with no hair; colours from a 24-entry table within the race's allowed hair colour range) and the armour textures (helm `IT<offset + 5000 + m>` on `HEAD_POINT` with show_helm, tunic 4010 + m / robe 4000 + (m − 10) on `TUNIC_POINT`, plate chest 6000 on `CHEST_POINT`, shoulder pairs 7000 + 2m, wrist pairs 8000 + 2m on `GAUNTR/L_POINT`, legs 4020 + m on `PELVIS_POINT`, feet pairs 9000 + 2m on `LEGL/R_POINT`, hands `0`; the hair goes when a helm took). `offset` is the race/sex item offset (30 for females + Human 360, Barbarian 540, Erudite 480, Wood elf 240, High elf 300, Dark elf 180, Half elf 60, Dwarf 120, Troll 660, Ogre 720, Halfling 780, Gnome 0, Iksar 420, Vah Shir 600, Froglok 840). Dag point names are `<code>HEAD_POINT_DAG`, …, `FIHANDL/R_TRACK`. Parts come from lgequip (Luclin), frogequip (Froglok) or EQG (hero's forge). Every part's `SetTint` colour multiplies it (RGB 0 is untinted).
- A skeletal WLD part's bones follow the body bone of the same name (`IT1012HAIR1_TRACK` → `HUMHAIR1_TRACK`) or else the dag point; static parts hang off the point. EQG pieces (hero's forge) on Luclin models: each vertex goes from the piece's bind space into its bone's space (piece bone `CHChest` → `<code>CHCHEST_TRACK`, else the nearest named ancestor, else the point), times the NewArmorAdjData matrix. A live client's colour of a piece (a `Resources/Layers/*.txt` row `piece^base^layer`) is its base mesh with the layer's textures; a chain of such rows is followed at most 8 deep (`EqgCharacterStore::kMaxLayerDepth`; live rows are one deep).

## EQG models

Hero's Forge attachments use `EqgCharacterStore::armor_part_mesh`, whose alias lookup takes precedence over a direct
item model or WLD actor of the same name. The requested name and the race/sex adjustment remain the attachment's;
only its geometry and layer are resolved. Its cache is separate from `part_mesh`, so ordinary held items, hair and
NPC parts retain their direct-first lookup, even when a modern armor mapping reuses their IT number. A row whose base
mesh is missing cannot be followed (`EqgCharacterStore::armor_alias` is false), so the piece resolves as it would with
no row at all: the direct EQG model, or on a Luclin model the WLD actor, plainly lit (a Hailstone policy for mixed
installs, as RoF2 itself reads no layer rows). When the base exists but its layer is unavailable, a pre-existing direct model
with matching bone, piece, vertex and triangle counts keeps its legacy rendering; this conservative compatibility
fallback preserves working armor in installations
with incomplete layer catalogs and rejects direct models with a different layout. A usable modern mapping always takes precedence. No game files
are changed or supplied. The modern/v2 armor revision uses the existing EQGM/EQGL formats, not a new wire format.
Whether a piece's materials draw their surface maps travels beside the mesh (`eqg_character::ArmorPart`, the
`surface_maps` argument of `append_pieces`), so a direct piece shares `part_mesh`'s cached mesh rather than a copy.
`append_pieces` gives two materials of the same name and diffuse one slot only when their surface maps and parameters
agree, so a plain part never takes an armor part's maps, whichever is appended first.

Layered armor applies the layer to every material of a copy of the base mesh. The layer's supplied C/N/E textures
replace the corresponding base shader properties; omitted textures retain the base maps. EQGL v3 supplies shininess
and environment strength 1; v4 stores both. These override existing material properties (`SetLayer` @0x10048130),
with the layer's environment strength copied as stored, unlike the initial mesh property's doubled value. The
parser retains these scalars only for v3/v4; older scalar tails remain unverified. Ordinary EQG NPC texture variants
keep their existing diffuse-only layer application. Armor surface maps and highlights are used by modern lighting
(docs/graphics.md "EQG surface maps"); the classic look retains its existing lighting.

Races whose code has no WLD actor load from EQG archives (`assets::EqgCharacterStore`): the mesh is the `EQGS`/`EQGM` entry `<CODE>_ACTORDEF` of `Resources/OnDemandResources.txt` (`archive^member^name^type`, e.g. `hnm.eqg^HNM.MDS^HNM_ACTORDEF^EQGS`), else `<code>.eqg` with `<code>.mds` / `<code>.mod`. Rodents (race 415, `RTN`, from `qeynos_chr.txt` `rtn,rtn`) and Qeynos guards (566, `HNM`/`HNF`, new-style flag 0x08) are the first users.

Layouts (all little-endian; after OpenEQ's `modern.rs`): header `magic, version (1–3), string bytes, material count`, then `bone count, piece count` (`EQGS`) or `vertex count, triangle count, bone count` (`EQGM`); the string table; materials `{id, name, shader, property count, {name, type, value}}` (type 2: a string offset; `e_TextureDiffuse0` is the texture); bones `{name, next sibling, child count, first child, translation xyz, rotation xyzw, scale xyz}`; per piece (`EQGS`: `{main flag, name, vertex count, triangle count, assignment count}`) vertices `{position, normal, [v3: colour u32], uv, [v3: 8 bytes]}`, triangles `{3 indices, material (−1 none), flags}`, and per vertex `{count ≤ 4, 4 × {bone, weight}}` (weights normalised). An `EQGM` puts its single piece's vertices and triangles before the bones. Stored rotations are the conjugate of the usual convention. A file with bones stores v running up from the bottom of the texture, so the reader turns v into 1 − v; read as stored, every EQG creature's and skinned hero's forge piece's texture lands upside down (teeth and paw pads on the puma's back, chainmail across a breastplate). A file without bones (a held item, a hero's forge helm or bracer) stores v from the top, as the zones' `.mod` objects do, and is read as stored; turned, the 10th anniversary shield IT14000's lettering is upside down and the Haunting Nightmares ornament IT101064 shows the inside of its pumpkin. Vertices are in bind (model) space, so the renderer multiplies each bone's animated matrix by the inverse bind matrix; vertices blend up to four bones.

`EQGA` animations: `magic, version, string bytes, track count, [version > 1: u32]`, strings, then per track `{frame count, bone name, frames {time ms, translation, rotation, scale}}`. Tracks match bones by name (case-insensitive). Clips are resampled to fixed frames at the longest track's mean key spacing (RTN walk 11 ms, HNM clips 66 ms), clamped to 10..200 ms; a clip is cut at 4096 frames (`eqg_character::kMaxClipFrames`, 13.6 minutes at 200 ms; stock clips run seconds), so a broken file's key times cannot ask for millions of poses. Names are `<ANIM>_<take>_<n>_<CODE>`; only `_BA_` takes are used, `_1` (IDLE `_2`, `_3` become O02, O03), mapped by `eqg_character::clip_code` (STND P01, IDLE O01, WALK L01, NRUN L02, JMPA L03, JMPU L04, FALL L05, CWLK L06, CLMB L07, CRCH L08, SWIM P06, NSIT P07, KNEL P05, CRMP D05, FLCH D01, STUN D02, KICK C01, PATK/STPR C02, SL2H C03, BL2H C04, SLPR/SATK C05, BLPR C06, BASH C07, MHA1 C08, NBOW C09, RKCK C11, MCST T02, GCST T03, DCST T04). A model's own animations come from the index and `<code>.eqg`; for clips it lacks the race table's animation fallback race is followed (flag 0x04): HNM → race 1 (HUM, no EQG anims) → race 522 (DKM, `dkm.eqg`/`dkm_anims.eqg`), so guards walk with Drakkin animations.

An EQG model has body pieces `<code><nn>` and head pieces `<code>HE<nn>` (HNM: HNM00, HNM07, HNMHE00–HNMHE07, each with its own materials). The appearance picks body `<code><TextureType>` and head `<code>HE<HeadType>`, falling back to `<code>`, `<code>00` / `<code>HE00`, then applies the TextureType's material layers: `"%02d"` of TextureType (0–30) selects the variant, and material i of the file (in file order) the layer `C_<code>_S<vv>_M<i + 1>` when one is loaded, and is left alone otherwise. Layers are the `EQGL` (`.lay`) members of the EQG archives (the client loads every member) and the `EQGL` lines of `OnDemandResources.txt` (`gbn.eqg^GBN.LAY^C_GBN_S01_M01^EQGL`); the first loaded name wins. Layout: `magic, version, string bytes, entry count`, strings, entries of 10 / 16 / 7 / 8 u32 for versions 1–4: the name, five texture names (−1 none) whose role is the character five from the end (`C` diffuse, `N` normal, `E` environment), then scalar fields (v3: shininess; v4: shininess and environment strength, used by armor as described above). Example, GUS (race 549, the small goo: a flat translucent blob with a skeleton and debris inside, `GUS_m00` body `Alpha_MaxCBS1` and `GUS_m01` debris): texture 1 is `C_GUS_BD_S01_C.DDS` (green) on the body with the debris unchanged, texture 4 `C_GUS_BK_S04_C.DDS` on body and debris (not `c_gus_bd_s04_c.dds`, which no layer uses), texture 5 the mercury `C_GUS_EV_S05_C.DDS`. A model with no layer for the variant replaces `_sNN` in texture names with TextureType where that file exists (a fallback rule). Bind-pose bounds: RTN z −0.01 … 1.49, HNM 0 … 6.0 — the origin is at the feet.

## Appearance

Armour records keep all five words of RoF2's ArmorProperties (type, variation, material, newArmorID, newArmorType; EQEmu's Texture_Struct Material, Unknown1, EliteMaterial, HeroForgeModel, Material2), as `Appearance::material`, `material_variation`, `elite_material`, `hero_forge` and `new_armor_type`. RefreshEquipSlot (@00594e50) stores the wire's record unchanged as the ActorClient's ArmorProperties (+0x8c, PlayerClient_SetActorEquipmentSlot @0042e6f0), so UpdateNewArmorSlot names a new-style model's texture `<code>_<material>_<variation>_<part>` and overlays `A_<code>_<material>_<variation>_S<elite material>` when the third word is set. Spawns, wear changes, character selection, item previews, appearance cache keys and saves carry the complete record. `Appearance::new_armor_bits` holds the `ActorNewArmorFilter` bits that show a spawn's hero's forge (PlayerClient_ApplyNewArmorFilter @0x595de0): 0x10 for an NPC; for a player 8, plus 1 for the local player, 2 for the local player or a group member, 4 for a raid member; none for a corpse (EQEmu sends NPC 2 for every corpse; RoF2 takes any Type above 1 as one). They are made when the spawn arrives and again when the group or raid changes; the renderer collapses them to shown or hidden for the active filter, so a membership change the filter does not see rebuilds nothing. `OP_Illusion` applies decoded Drakkin heritage, tattoo and detail changes; zero resets a feature and the omitted-value sentinel keeps it.

`game::Appearance` (on `game::Spawn`) holds TextureType, HeadType, face, hair/beard style and colour, eyes, Drakkin features, show_helm, and per slot (0 head, 1 chest, 2 arms, 3 wrists, 4 hands, 5 legs, 6 feet, 7 primary, 8 secondary) the complete five-word armor record and tint (`0xAARRGGBB`, Tint_Struct). It comes from the spawn packet (`GameConnection::apply_spawn`), `OP_WearChange` and `OP_Illusion`; `ActorRenderer` rebuilds a spawn's mesh when it changes, dressing `game::drawn_appearance`: a race outside the per-slot armour races (1-12, 128, 130, 330, 522) shows no armour colours (slots 0-6), as the RoF2 client draws a player under a skeleton illusion (docs/unknowns.md).

Which value drives what:

- PC-model races (race < 13, 128, 130, 330, 522) always dress per slot: a TextureType ≥ 0 in the spawn becomes the material of slots 1–6 (`normalize_appearance`). Other races with TextureType ≥ 0 wear that body texture on every part and ignore armour; `OP_WearChange` to their slots 0–6 is ignored, slots 7/8 still change.
- OP_WearChange (27 bytes: `u16 spawn, 5 × u32 armour {material, ?, elite, hero's forge, ?}, u32 tint, u8 slot`): material −1 resets the slot.
- The own model after a gear change (`refresh_worn_slot`, no OP_WearChange comes for it) shows each worn item with its ornament (`game::worn_look`): a held item the model of its ornament strings (`IT<n>`), armour its own Material with the ornament's hero's forge model; a disabled ornament (the first type 20/21 socket's augment with its stats disabled) shows the plain item (PcClient_RefreshWornSlotVisual @0x4919b0). An ornament augment's own Material is not shown, since EQEmu shows everyone, and the player at zone-in, the item's.
- The head of a PC-model race shows its armour only with spawn bit 23 (show_helm) set; head material 7 is drawn as 2.
- Robes: chest 10–16; arms and wrists then show the chest's material. On a Luclin model they also take the chest's tint and hero's forge flag, and a Froglok's legs do the same (`PlayerClient::HandleMaterialEx` @0x594e50; `game::luclin_armor_slot`).

Classic (WLD) dressing (`dress_wld`): the skeleton's meshes, with `<code>HE00_DMSPRITEDEF` replaced by `<code>HE<nn>` for the head material (NPC body textures: HeadType) and `<code>_DMSPRITEDEF` by `<code>01_DMSPRITEDEF` under a robe, when they exist. Texture names `<code(3)><part(2)><variant(2)><piece(2)>` (parts HE CH UA FA HN LG FT) get the slot's material as variant (robes 10–16 → 04–10), when that file exists in any archive: `HUMCH0001` → `HUMCH0301` for plate. Head textures keep their variant (body textures: HeadType's, else TextureType's) and take the face as the piece's tens digit (`HUMHE0011` = face 1). Robe body textures `CLK<vv><nn>` take chest − 6. Each material gets its slot's tint when the slot's material is not 0 and, for materials 1–99, that variant's texture exists (SwapBodyMaterial's ReplaceMaterial fails, colour and all, when the new material is not loaded: SKE has chest variants 00–04 only, so material 5 leaves its chest as it was, untinted) (heads: when the variant is not 00, so bare skin stays untinted); tints whose colour is black or white count as none.

Held items (slots 7, 8): the material is the item's model number `IT<n>` (IDFile). Static items (0x2d meshes) are in grip space; skeletal ones are baked in their rest pose. Classic and Luclin models carry them on `<code>R_POINT_TRACK` / `<code>L_POINT_TRACK`, a secondary on `SHIELD_POINT` when its model number is a shield to `CDisplay::IsShield` @0x489d70 (`game::is_shield_model`: IT200..228, 10530..10544, 10664..10671, 11001..11020, 11496..11497 and 25 single numbers such as 14000; the original asks `Resources\ActorTagInfo.txt` first when it loaded, and RoF2 ships none). Texture names do not count: the Haunting Nightmares Shield Ornament (IT101064, `shield_round_halloween_c.dds`) is held in the hand on `L_POINT`, which is how its face comes to point outward. Hailstone adds, as a deliberate difference (`display.extra_shields`, on by default), 271 later shield models RoF2 does not list and so holds in the hand like a weapon: `src/game/shield_models.inc`, made by `tools/gen_shield_models.py` from an EQEmu items table and the game folders. 154 are models that shield items, type 8, make up most of the non-augment uses of (not the placeholder IT63 or the weapon models a few shields borrow). The other 117 are shield ornaments' models that no other item uses: the items table does not say what an ornament fits, so the generator measures each such model's EQG mesh and takes it when it is flat and covers most of its box seen from the broad side, as every listed shield does and the weapon ornaments (axes, swords, hammers) do not, plus seven shields the measure misses (`SEEN_SHIELDS`). With them, the Haunting Nightmares ornament (IT101064, and IT101068 in its second colours) is worn on the forearm like the other shield ornaments, its iron back outward, where RoF2 holds it in the hand face outward (`SEEN_SHIELDS`); matching is exact (`find_bone`, so `HAIR_POINT` is not `R_POINT`). EQG models use `ARMR_WEAP`, `ARML_WEAP`, `ARML_SHLD` and the bone's bind matrix. Items are not tinted (`itmt.ini[Primary/SecondaryTintIndex]` is not read).

Tints: RGB 0 becomes white, so black means untinted. Armour colours are `RGB | 0xff000000`; hero's forge pieces are untinted. Classic models draw `lit × Tint.rgb`.

New models of the classic races (Drakkin, `DKM`/`DKF` from `dkm.eqg`): the facial features go through `Resources/PlayerCustomization.txt` (`{race, heritage, gender}`: counts, `COLOR_LIST`, `BASE_COLOR`, values clamped to the counts): face texture `C_<code>_HEAD_S%02d_M01`, hair `<code>_HAIR_%02d` (dag 8) and beard `<code>_FACIALHAIR_%02d` (dag 9) tinted `COLOR_LIST[colour]`, tattoo `<code>_TATTOO_00` (dag 0x19, texture `A_<code>_TATTOO_S%02d_M01`) and facial attachment `<code>_FACIALATT_%02d` (dag 0x18), both tinted with the heritage's `BASE_COLOR`. Then per slot: `<code>_<a>_<b>_<bone>` (`a` the normalised slot texture id, `b` the variation, the bone the part's slot: head `CHEST_CHEST02`, chest `ROOT_BODY`, arms `CHEST_CHEST01`, wrists `ARMR/L_CLAV`, hands `ARMR/L_BCEP`, legs `PELV`, feet `LEGL/R_THGH`), robe overlays `A_<code>_<a>_<b>_S<c>`, tinted with the slot tint. The parts are `<name>.mod` files whose bones follow the body's by name. The head material is matched by texture family (`c_dkm_head_s`), as the palette order is not the file's.

Hero's forge (`newArmorID`): the tag for (id, code) is looked up unless `ActorNewArmorFilter` (eqclient.ini, default 24: players 8 and NPCs 0x10; 1 self, 2 group, 4 raid) hides it (`Appearance::new_armor_bits` above); `NewArmorTagData.txt`'s `*` / `L` / `N` tags expand to the race table's codes with flags 0x20 / 0x20 without 8 / 0x28 (M / F one gender; a later line replaces a record). The tag's `IT<number>` (and `IT<pair>` on the second part) replaces the slot's part, with `NewArmorAdjData` (`RotationYawPitchRoll(rx°, ry°, rz°)`, rows × s, + t) unless the tag ignores adjustment; Hide Mesh hides the body slot's meshes, Show Hair keeps the hair under a helm. Pieces are EQG `.mod` entries of `OnDemandResources.txt` (`genericplate.eqg`); bone-less ones are static.

NPC tints: for new-style races (flag 0x08): `npct.ini` Value<index> (entry index − 1) on the whole actor (not its held items); index 0 or past the table does nothing. From the spawn packet's NpcTintIndex and `OP_SpawnAppearance` 39; 43 sets show_helm. `npct.ini` and `itmt.ini` hold `[Data] Number` entries, `Value1..ValueN` (default 0xffffff), alpha forced to 0xff (ColorTable_LoadFromIni @0x574b60). Deliberate difference: the original takes any positive Number; the client reads at most 65536 entries, so a forged file in a server's asset folder cannot make it fill billions.

Appearances are cached per model and appearance key in the library (geometry) and per mesh on the GPU. The renderer builds a new appearance on a worker thread (`core::LatestJobs`, one per renderer, started on first use): the dress, then the new mesh's CPU side (its vertices for the GPU, its textures read, decoded, composited for Luclin layers and their mips built; each texture read once, `TextureClaims`). The main thread applies the finished ones in `prepare_spawns` while a frame's time for them lasts (`set_build_budget_ms`: 4 ms in the open, 100 ms behind the loading screen; the first of a frame is always applied): their buffers and new textures staged and the descriptors written. Meanwhile the spawn is drawn in its previous mesh, or the model's default one; a look the renderer has applied before for the same model (a spawn coming back past the actor clip, a crowd in one uniform) is taken at once. Only a spawn's latest request counts: a newer appearance supersedes the one being built, a spawn that leaves (or goes past the actor clip) drops its request, and a result is applied only for the model and look its spawn still asks for. The worker is stopped (the appearance it is building finished, the rest dropped) before the renderer goes or hands its meshes to the next zone (`release_kept`). The library is safe to use from both threads: every call that reads or fills its caches, the shared cache or the EQG and model-archive stores holds one mutex, shared by the libraries of one `CharacterArchiveCache`; texture decoding runs outside it. A spawn's default mesh put up for the first time is still made on the main thread, and charged to the budget. All of a frame's new meshes and textures go to the GPU in one submission, with one fence wait, before the frame's commands are submitted (`stats().upload_ms`; the perf window's frame sections "actors new appearances" and "actors upload"). Live in South Qeynos (170 spawns): 0.1–2 ms per frame for 4 appearances while the zone fills, about 100 appearance meshes and 770 textures after a minute, 6 frames whose texture uploads took 9–14 ms, then nothing.

## Race → model

`race_models.inc` is generated (`tools/gen_race_models.py`) from the model table: 859 rows, 731 race ids, gender 0 male, 1 female, 2 neutral. The pair is looked up exactly, falling back to HUM/HUF. `find_race_model` instead tries the exact gender, then 2, 0 and 1, because EQEmu sends single-model NPC races with any gender. Codes without a WLD actor try the EQG store; races with neither fall back to the box. With the global archives, 148 of the 731 race ids have a classic model (`chrdump --sweep`); a zone's own archives add more.

Before the lookup, CreatePlayerActor swaps elementals (`luclin_elemental_swap` in `game/world_state.h`, run by `WorldState::make_actors`). eqclient.ini `[Defaults] UseLuclinElementals` (CDisplay +0x129, default TRUE, read as GetEQClientIniBool reads: T, t or 1) decides the direction. On, race 75 (`ELE`, one body with four skins: 0 earth, 1 fire, 2 water, 3 air) becomes the typed Luclin elemental from `global5_chr`: texture 0 → 209 `EEL`, 1 → 212 `FEL`, 2 → 211 `WEL`, any other → 210 `AEL`, with texture and HeadType 0 (the typed models have one skin). When the typed model is not loaded the spawn stays race 75 with its texture. Off, races 209–212 become race 75 with texture 0 / 1 / 2 / 3. The spawn's race really changes (SetRace), as with the HUM fallback. This is why EQEmu's magician pets (race 75 with the element in the texture) are drawn with the Luclin models by default.

## Size and floor placement

For a classic model the drawing scale is Height × 0.2 (Height ≤ 0 → 6, so a size-6 human is drawn at 1.2), and the avatar height is moddat.ini `ROffset` (default 3.125) × scale = 3.75 for a size-6 human. That matches the 3.75 units the live server puts a standing human above the floor, and a size-3.5 halfling standing 2.125 above the same floor (3.125 × 0.7 = 2.19). The renderer therefore draws the model origin at the spawn's z, scaled by size × 0.2, with no per-model offset; the rest-pose soles of the classic player models are 2.5–3.2 units below the origin (dwarves 2.53, so they may float slightly). New-style races (flag 0x08) scale by Height / 6 × 1.3 and classic ones by Height × 0.2 (both / 1.3 until the first OP_NewZone); EQG models have their origin at the feet and the animation loader lowers their ROOT_BONE by moddat.ini's ROffset, so they are drawn ROffset × scale below the spawn's z. The rules are in `game/spawn_heights.h`.

## Rendering

An EQG armor piece attached to a WLD body keeps its bind-space vertices and up to four weights. Each influence gets a mesh-local palette entry containing the matched host bone and its adjustment/inverse-bind correction; missing named bones keep the existing nearest-ancestor rule. The same palette is evaluated for scene/shadow rendering and CPU picking. Boneless pieces keep a rigid anchor/adjustment binding. Analytical fixtures check the multi-joint result and invalid-palette handling.

`ActorRenderer` uploads a mesh's vertices (position, normal, uv, four bone indices and weights) and indices the first time a spawn uses it (a model's default mesh or an appearance). Each frame it samples every instance's clip on the CPU, folds the instance transform (and for EQG models the inverse bind matrices) into the bone matrices, and writes them to a per-frame storage buffer (64k matrices); a push constant gives the instance's first bone, the texture slot and the part's tint, which multiplies the texture. Textures share one bindless array per renderer; each frame's descriptors update after its own fence. Idle model eviction retires texture slots only after the GPU completion point and only when no surviving model reads them. A texture rejected because the array was full retries after capacity is reclaimed (checked on the one-second look sweep): a model no spawn wears is dropped at once, but a worn one is rebuilt on the main thread at its next draw (its textures read there), so only one worn model is retried a sweep. Genuinely missing images remain cached. Materials map to passes like zone materials (`render/material_state.h`): masked parts alpha-test at 0.5, transparent ones blend, additive ones add; EQG `Alpha_*` blend with a 16/255 test, `Chroma_*` test at 192/255, `AddAlpha` adds unfogged. Back faces are culled (WLD fronts clockwise, EQG counter-clockwise in this frame; two-sided materials not culled). Cross-fades last 100 ms, 175 ms into P01/O01 . Fog matches `zone.frag`; a soft key light (0.8 + 0.25·N·L) keeps bodies readable while the zone is full-bright.

Animation choice per spawn (`draw_spawns`): the clip, its direction and rate come from `game/spawn_animation.h`, which chooses as the original's two animation objects do (`game/mechanics/anim_select.h`): classic models from the movement speed and stand state (sitting down plays P02 once, then holds P07 with O03 as the fidget; standing up plays P02 reversed), new-style (EQG) models through PlayerAnimation_SelectMovementAnim. Clip changes cross-fade as above. Corpses play D05 once and hold it.

Live check (North Qeynos, 45 modelled spawns in view range): 553 draws, about 0.15 ms CPU per frame for sampling and recording.

### Memory diagnostics

Loading global character archives logs one `memory archive:` line per archive (debug level) and a `memory archives:` total (info). Zone archives get the same breakdown on each load. Values are MiB: mapped file length, owned archive heap bytes, and an estimate of parsed WLD payloads. Mapped length is not resident memory; parsed estimates exclude indices, allocator overhead and unused capacity. Models, dressed meshes and EQG caches are outside these WLD totals. Global totals are logged on first load or asset invalidation, not repeated on every zone change.

The playable client's `memory checkpoint:` lines report process resident memory after startup stages, before unloading a zone and during zone loading (debug level), and after appearances settle (info, once per zone-in). Adjacent `memory GPU:` lines report VMA allocation bytes per heap, not driver heap budgets. Do not add GPU allocations to RSS, particularly on integrated GPUs. Asynchronous sound, navigation and model loading can overlap checkpoints; differences identify stages to investigate, not exact ownership. Capture a fresh start through a settled zone-in from `logs/hailstone.log`, then compare a second zone load. On Windows, the same checkpoints also log `private commit` from `PROCESS_MEMORY_COUNTERS_EX::PrivateUsage`; the performance window shows it alongside resident memory. Private commit measures private committed allocation, including pages outside the working set; it is not added to RSS or GPU totals. Other systems leave this measurement unavailable instead of substituting virtual size or resident memory. These diagnostics do not provide a complete heap census.

Deferred character WLD diagnostics: `memory WLD materialized:` records decodes at debug level; normal logs use cumulative decode/release counters to avoid a line for every rebuild. After zone settling, `memory character WLDs:` reports materialized/total WLDs and the combined compact-index and decoded-payload estimate across unique archives in the current library, and the retained set's estimate against its budget. The earlier per-archive parsed estimate now includes compact indices for unloaded WLDs. Compare fresh-start and repeated-zone runs; this does not account for all character name-table, model, appearance-cache or allocator storage. Source WLD payloads go to the retained set after the last scoped reader and are released from it past its budget; their compact indices and completed model/appearance caches remain. First use of another appearance reparses a source WLD only when it has left the retained set, trading decoding work for a bounded retained baseline. Cache hits do not need the source WLD. Finer-grained fragment loading remains future work.

`memory character WLD activity:` reports cumulative decodes and releases for the current library's unique archives; counts can change when zone-only archives go away. `memory character caches:` estimates the unique model and appearance payloads reachable through the current library, the cross-zone shared cache, persistent EQG model stores and opened standalone libraries. Shared objects count once; item cache entries own copies and each copy counts. Estimates include object sizes, geometry, animation keys, material strings, points and emitters using vector/string sizes, not capacities. They exclude cache keys/maps, lookup records, reference-count control blocks, parsed EQG source meshes/parts/layers, renderer-owned copies and allocator overhead; small inline strings can be overestimated. This snapshot is serialized with construction but is not a process-wide heap census. Freed WLD allocations return to the system allocator, which may retain pages, so release counts do not promise an equal RSS or commit drop.

`memory model breakdown:` splits the model subtotal into animation/skeleton (clip tracks and keys, clip/held aliases, bone names, parent/order and inverse-bind arrays), geometry/materials (vertices, indices, parts and owned material payloads), and other (the model object, identifying strings, points and emitters). These categories sum to the model payload estimate and use the same object deduplication as the cache total. Geometry excludes image pixels and GPU allocations. Compare category growth with private commit at settled zone checkpoints; the remaining gap can include other live allocations, reserved allocator pages and driver allocations, and does not by itself prove a leak or fragmentation.
